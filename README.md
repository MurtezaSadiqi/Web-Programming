    <h1>جواب سوال اول:</h1> 
هر دو دستور `merge` و `rebase` برای ترکیب تغییرات شاخه‌ها در Git استفاده می‌شن، ولی روش کارشون فرق داره.

<h3>:git merge</h3>

این دستور تغییرات دو شاخه رو با هم ترکیب می‌کنه، بدون اینکه تاریخچه کامیت‌های قبلی تغییر کنه. اگه دو شاخه جداگانه تغییر کرده باشن، معمولاً یه Merge Commit جدید هم ساخته می‌شه.

مثلاً:


git switch main
git merge feature-login


به نظرم این روش برای کارهای گروهی بهتره، چون تاریخچه تغییرات هر شاخه حفظ می‌شه و بعداً می‌تونیم بفهمیم چه تغییراتی انجام شده.

<H3>:git rebase</H3>

این دستور کامیت‌های شاخه فعلی رو روی آخرین وضعیت یه شاخه دیگه دوباره اعمال می‌کنه. این کار باعث می‌شه تاریخچه کامیت‌ها خطی و مرتب‌تر بشه، ولی شناسه کامیت‌های دوباره اعمال‌شده تغییر می‌کنه.

مثلاً:


git switch feature-login
git rebase main


از این روش وقتی استفاده می‌کنم که روی شاخه شخصی خودم کار می‌کنم و می‌خوام تغییرات جدید `main` رو هم داشته باشم.

تفاوت اصلی:

در کل، `merge` تاریخچه شاخه‌ها رو حفظ می‌کنه و ممکنه یه کامیت جدید برای ادغام بسازه، ولی `rebase` کامیت‌ها رو دوباره اعمال می‌کنه تا تاریخچه خطی‌تر بشه. به همین خاطر بهتره روی شاخه‌های مشترک بدون هماهنگی از `rebase` استفاده نکنیم.

<H1>جواب سوال دوم:</H1>
<h3 dir="rtl"><span dir="ltr">Hunk</span> چیه؟</h3>
وقتی یه فایل رو تغییر می‌دیم و با دستور `git diff` تغییراتش رو می‌بینیم، Git تغییرات نزدیک به هم رو به بخش‌هایی تقسیم می‌کنه که به هر کدوم Hunk می‌گن.

چطور فقط بعضی تغییرات رو کامیت کنیم؟

مثلاً اگه داخل فایل `index.html` چندتا تغییر داده باشیم ولی نخوایم همه‌شون رو کامیت کنیم، از این دستور استفاده می‌کنیم:


git add -p index.html


این دستور تغییرات رو بخش‌به‌بخش نشون می‌ده و می‌تونیم با گزینه `y` بخش موردنظر رو انتخاب کنیم، با `n` ازش رد بشیم و با `s` در صورت امکان به قسمت‌های کوچک‌تر تقسیمش کنیم.

بعد با دستورهای زیر تغییرات انتخاب‌شده رو بررسی و کامیت می‌کنیم:


git diff --cached
git commit -m "Update selected changes"


فایده این کار چیه؟

این روش باعث می‌شه تغییرات نامرتبط رو توی یه کامیت قرار ندیم. مثلاً تغییر ظاهر سایت و رفع یه باگ رو جداگانه کامیت کنیم. این‌طوری تاریخچه پروژه مرتب‌تر می‌شه و بعداً بررسی یا برگردوندن تغییرات هم راحت‌تر خواهد بود.
<H1>جواب سوال سوم:</H1>
git bisect چیه؟

این دستور برای پیدا کردن کامیتی استفاده می‌شه که باعث ایجاد یه خطا در پروژه شده. روش کارش هم جست‌وجوی دودویی هست؛ یعنی به جای بررسی همه کامیت‌ها، هر بار تقریباً وسط محدوده رو بررسی می‌کنه.

مراحل انجام کار:

اول جست‌وجو رو شروع می‌کنیم و یه کامیت سالم و یه کامیت خراب رو مشخص می‌کنیم:

git bisect start 
git bisect bad N326 
git bisect good a123

بعد Git یه کامیت میانی رو انتخاب می‌کنه. ما پروژه رو تست می‌کنیم و اگه سالم بود git bisect good و اگه خطا داشت git bisect bad رو می‌زنیم.

این کار ادامه پیدا می‌کنه تا کامیتی که خطا رو وارد کرده پیدا بشه. در آخر هم با دستور زیر از حالت جست‌وجو خارج می‌شیم:

git bisect reset

مثال و فایده:

مثلاً اگه دکمه Login سایت قبلاً کار می‌کرده ولی الان خراب شده، می‌تونیم با این روش کامیتی رو که باعث مشکل شده پیدا کنیم.

فایده‌اش اینه که لازم نیست همه کامیت‌ها رو یکی‌یکی بررسی کنیم و مخصوصاً وقتی تعداد کامیت‌ها زیاده، خیلی سریع‌تر به منشأ خطا می‌رسیم.

<h1>جواب سوال چهارم</h1>
1: بررسی وضعیت تغییرات

برای اینکه بفهمیم کدوم تغییرات آماده کامیت هستن و کدوم هنوز وارد Staging نشدن، از این دستورها استفاده می‌کنیم:

git status 
git diff 
git diff --staged

دستور اول وضعیت کلی فایل‌ها رو نشون می‌ده. دستور دوم تغییراتی رو نشون می‌ده که هنوز وارد Staging نشدن و دستور سوم تغییراتی رو نشون می‌ده که آماده کامیت هستن.

2: کدوم تغببرات کمیت میشن؟
اگه فایل README.md رو تغییر بدیم و با git add وارد Staging کنیم، بعد دوباره ویرایشش کنیم ولی git add نزنیم، فقط همون تغییرات قبلی که وارد Staging شدن کامیت می‌شن. تغییرات جدیدتر داخل Working Tree باقی می‌مونن، چون Git موقع کامیت از نسخه موجود در Staging استفاده می‌کنه.

3: جلوگیری از اضافه شدن فایل‌های موقتی

برای اینکه فایل‌های پوشه tmp/ وارد کامیت‌های بعدی نشن، داخل فایل .gitignore این خط رو می‌نویسیم:

/tmp/

این کار باعث می‌شه Git فایل‌های Untracked داخل این پوشه رو نادیده بگیره.

ولی اگه فایلی از قبل Tracked شده باشه، این روش به‌تنهایی کافی نیست و باید با دستور زیر اون رو از ردیابی Git خارج کنیم:

git rm --cached path/to/file

این دستور فایل رو از Staging و ردیابی Git خارج می‌کنه، ولی نسخه موجود روی کامپیوتر رو حذف نمی‌کنه. برای ثبت این تغییر هم باید کامیت انجام بدیم.
<h1>جواب سوال پنچم:</h1>
1: چرا Conflict اتفاق می‌افته؟

وقتی دو شاخه مثل main و feature-description یک خط مشترک از فایل README.md رو به شکل متفاوت تغییر بدن، موقع Merge ممکنه Git نتونه خودش تصمیم بگیره کدوم تغییر رو نگه داره. به این حالت Merge Conflict می‌گیم.

2: چطور Conflict رو پیدا و حل کنیم؟

اول روی شاخه main دستور زیر رو می‌زنیم:

git merge feature-description

اگه Conflict وجود داشته باشه، Git پیام خطا می‌ده و با دستور git status هم می‌تونیم فایل‌های دارای تداخل رو ببینیم.

داخل فایل علامت‌های <<<<<<< HEAD و ======= و >>>>>>> feature-description دیده می‌شن که تغییرات دو شاخه رو مشخص می‌کنن.

برای حل مشکل، فایل رو دستی ویرایش می‌کنیم، تغییرات هر دو شاخه رو نگه می‌داریم و علامت‌های Conflict رو حذف می‌کنیم.

3: تکمیل Merge

بعد از حل تداخل، دستورهای زیر رو اجرا می‌کنیم:

git add README.md 
git commit -m "Resolve merge conflict"

با دستور git status وضعیت پروژه رو بررسی می‌کنیم و خود فایل رو هم چک می‌کنیم تا مطمئن بشیم هیچ علامت Conflict باقی نمونده.

4: لغو Merge

اگه بخوایم قبل از تکمیل Merge عملیات رو لغو کنیم، از دستور زیر استفاده می‌کنیم:

git merge --abort

این دستور تلاش می‌کنه پروژه رو به وضعیت قبل از شروع Merge برگردونه.
<h1>جواب سوال ششم:</h1>
1: حذف تغییرات قبل از Staging
فرض کنیم فایل notes.txt رو تغییر دادیم، ولی هنوز git add نزدیم و حالا می‌خوایم تغییراتش رو حذف کنیم.

git restore notes.txt

این دستور فایل رو به نسخه موجود در Staging برمی‌گردونه و تغییرات Stage نشده رو حذف می‌کنه. خود Staging و تاریخچه کامیت‌ها هم تغییر نمی‌کنن.

2: خارج کردن فایل از Staging بدون حذف تغییرات

اگه فایل رو با git add وارد Staging کرده باشیم، ولی بخوایم از اون خارجش کنیم و تغییراتمون باقی بمونه، از این دستور استفاده می‌کنیم:

git restore --staged notes.txt

این دستور نسخه Staging فایل رو به آخرین کامیت برمی‌گردونه، ولی تغییرات داخل Working Tree رو نگه می‌داره. تاریخچه کامیت‌ها هم دست‌نخورده باقی می‌مونه.

3: برگردوندن یک کامیت اشتباه که Push شده

فرض کنیم یک کامیت اشتباه رو روی شاخه مشترک main به GitHub فرستادیم و حالا می‌خوایم اثرش رو برگردونیم.

git revert abc123 
git push origin main

اینجا abc123 شناسه کامیت اشتباهه. دستور git revert یک کامیت جدید می‌سازه که تغییرات کامیت قبلی رو خنثی می‌کنه و دستور دوم اون رو به GitHub می‌فرسته.

در این حالت Working Tree و Staging بعد از تکمیل موفق عملیات با نتیجه کامیت جدید هماهنگ می‌شن و تاریخچه قبلی هم حذف یا بازنویسی نمی‌شه.

چرا از reset استفاده نمی‌کنیم؟

چون این کامیت قبلاً روی شاخه مشترک Push شده و ممکنه بقیه هم ازش استفاده کرده باشن. دستور git reset می‌تونه تاریخچه محلی رو عقب ببره و برای جایگزین کردن تاریخچه منتشرشده به Force Push نیاز بشه. برای همین git revert انتخاب امن‌تریه.
