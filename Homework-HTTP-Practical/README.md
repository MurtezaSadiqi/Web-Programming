# تمرین عملی HTTP — پراکسی معکوس با احراز هویت JWT

## سؤال اول: چطور می‌تونیم یک سرویس رو فقط داخل شبکه داخلی اجرا کنیم؟

برای اینکه یک سرویس از اینترنت به‌صورت مستقیم قابل دسترسی نباشه، باید اون رو فقط داخل شبکه داخلی اجرا کنیم و اجازه ندیم پورتش از بیرون در دسترس باشه.

در این پروژه، سرویس httpbin رو داخل شبکه خصوصی Docker قرار دادم و پورت اون رو روی سیستم اصلی منتشر نکردم. به این شکل، کاربران بیرونی نمی‌تونن مستقیم به سرویس دسترسی داشته باشن و درخواست‌ها باید از طریق پراکسی عبور کنن.

برای این کار، در فایل تنظیمات Docker از گزینه `expose` برای سرویس داخلی استفاده کردم و گزینه `ports` رو فقط برای پراکسی گذاشتم. همچنین شبکه داخلی رو از شبکه عمومی جدا کردم تا سرویس اصلی از بیرون قابل دسترسی نباشه.

در یک شبکه واقعی هم می‌شه با استفاده از آدرس‌های خصوصی و تنظیمات فایروال، دسترسی مستقیم از اینترنت رو محدود کرد.

## سؤال دوم: فلسفه استفاده از TLS Termination چیه؟

روش TLS Termination برای این استفاده می‌شه که ارتباط امن و رمزنگاری‌شده کاربران در خود پراکسی مدیریت بشه، نه در سرویس اصلی.

مثلاً فرض کنیم یک سرویس قدیمی داریم که از HTTPS پشتیبانی نمی‌کنه. به‌جای اینکه کد اون سرویس رو تغییر بدیم، می‌تونیم یک پراکسی معکوس جلوی اون قرار بدیم.

در این حالت، کاربر درخواست خودش رو از طریق HTTPS می‌فرسته و پراکسی اطلاعات رو رمزگشایی می‌کنه. بعد درخواست رو به سرویس داخلی منتقل می‌کنه و پاسخ رو دوباره به کاربر برمی‌گردونه.

مزیت این روش اینه که لازم نیست هر سرویس جداگانه گواهی امنیتی داشته باشه و تنظیمات مربوط به HTTPS همگی در یک محل مدیریت می‌شن.

البته اگه ارتباط بین پراکسی و سرویس داخلی از یک شبکه غیرقابل اعتماد عبور کنه، بهتره اون بخش هم رمزنگاری بشه.

در این کارخانگی، روش TLS Termination رو فقط توضیح دادم و پیاده‌سازی نکردم؛ چون در بخش عملی، استاد استفاده از احراز هویت JWT و دریافت درخواست‌ها از پورت ۸۰ رو خواسته بود.

## سؤال سوم: پیاده‌سازی پراکسی معکوس با احراز هویت JWT

### توضیح کلی پروژه

برای این بخش، یک پراکسی معکوس با استفاده از Node.js ساختم و از Docker برای اجرای سرویس‌ها استفاده کردم.

پروژه من دو سرویس اصلی داره:

**سرویس اول: httpbin**

این سرویس نقش یک برنامه قدیمی رو داره که خودش سیستم احراز هویت نداره. سرویس رو روی پورت داخلی ۸۰۸۰ اجرا کردم و اجازه ندادم از بیرون به‌صورت مستقیم قابل دسترسی باشه.

**سرویس دوم: پراکسی معکوس**

این بخش درخواست‌های کاربران رو دریافت می‌کنه و قبل از فرستادن اون‌ها به سرویس اصلی، توکن JWT رو بررسی می‌کنه.

پراکسی داخل کانتینر روی پورت ۳۰۰۰ اجرا می‌شه و از طریق پورت ۸۰ سیستم اصلی در دسترس قرار می‌گیره.

### نحوه کار احراز هویت

برای ورود به سیستم، یک مسیر به نام `/login` در نظر گرفتم.

کاربر نام کاربری و رمز عبور خودش رو به این مسیر می‌فرسته. اگه اطلاعات درست باشه، سرور یک توکن JWT با اعتبار یک ساعت ایجاد می‌کنه و به کاربر برمی‌گردونه.

بعد از اون، کاربر باید توکن خودش رو در هدر Authorization درخواست‌های بعدی قرار بده.

اگه توکن معتبر باشه، پراکسی درخواست رو به سرویس داخلی httpbin می‌فرسته. اما اگه توکن وجود نداشته باشه یا معتبر نباشه، درخواست با کد وضعیت ۴۰۱ رد می‌شه.

### نحوه راه‌اندازی پروژه

برای اجرای پروژه، اول باید Docker Desktop روی سیستم نصب و اجرا شده باشه.

بعد فایل نمونه تنظیمات رو کپی می‌کنیم تا فایل اصلی تنظیمات ساخته بشه.

در ترمینال PowerShell دستور زیر رو اجرا می‌کنیم:

</div>

```powershell
Copy-Item .env.example .env
```

<div dir="rtl" align="right">

بعد داخل فایل `.env` نام کاربری، رمز عبور و کلید محرمانه JWT رو مشخص می‌کنیم.

این فایل نباید داخل GitHub قرار بگیره، چون اطلاعات محرمانه پروژه داخل اون ذخیره می‌شن.

حالا برای ساخت و اجرای کانتینرها دستور زیر رو اجرا می‌کنیم:

</div>

```powershell
docker compose up --build -d
```

<div dir="rtl" align="right">

برای بررسی وضعیت سرویس‌ها هم از این دستور استفاده می‌کنیم:

</div>

```powershell
docker compose ps
```

<div dir="rtl" align="right">

در صورت اجرای درست، هر دو سرویس باید در وضعیت اجرا باشن و پورت ۸۰ سیستم به پورت ۳۰۰۰ پراکسی متصل شده باشه.

اگه پورت ۸۰ روی سیستم اشغال باشه، می‌شه برای تست محلی اون رو موقتاً به پورت دیگه‌ای مثل ۸۰۸۸ تغییر داد.

### تست اول: ارسال درخواست بدون توکن

برای اینکه مطمئن بشم سرویس بدون احراز هویت قابل استفاده نیست، دستور زیر رو اجرا کردم:

</div>

```powershell
curl.exe -i http://localhost/get
```

<div dir="rtl" align="right">

**نتیجه تست:**

سرور کد وضعیت `401 Unauthorized` رو برگردوند و پیام زیر نمایش داده شد:

</div>

```json
{"error":"Missing or invalid JWT"}
```

<div dir="rtl" align="right">

این نتیجه نشون داد که پراکسی درخواست‌های بدون توکن معتبر رو رد می‌کنه.

### تست دوم: ورود و دریافت توکن JWT

در مرحله بعد، با استفاده از نام کاربری و رمز عبوری که داخل فایل `.env` تنظیم کرده بودم، درخواست ورود فرستادم.

برای این کار از دستورهای زیر استفاده کردم:

</div>

```powershell
$body = @{
    username = "student"
    password = "your-password"
} | ConvertTo-Json

$response = Invoke-RestMethod -Uri "http://localhost/login" -Method Post -ContentType "application/json" -Body $body

$response
```

<div dir="rtl" align="right">

در این دستورها باید نام کاربری و رمز عبور رو مطابق اطلاعات فایل `.env` وارد کنیم.

**نتیجه تست:**

درخواست ورود موفق بود و سرور یک توکن JWT برگردوند.

این یعنی بخش ورود و ایجاد توکن درست کار می‌کنه.

### تست سوم: ارسال درخواست با توکن معتبر

بعد از دریافت توکن، اون رو داخل یک متغیر ذخیره کردم:

</div>

```powershell
$token = $response.token
```

<div dir="rtl" align="right">

سپس درخواست جدیدی همراه با توکن به پراکسی فرستادم:

</div>

```powershell
curl.exe -i http://localhost/get -H "Authorization: Bearer $token"
```

<div dir="rtl" align="right">

**نتیجه تست:**

این بار سرور پاسخ زیر رو برگردوند:

</div>

```text
HTTP/1.1 200 OK
```

<div dir="rtl" align="right">

همچنین اطلاعات مربوط به درخواست از سرویس httpbin دریافت شد.

این نتیجه نشون داد که پراکسی توکن معتبر رو قبول کرده و درخواست رو با موفقیت به سرویس داخلی منتقل می‌کنه.

### جمع‌بندی تست‌ها

| نوع تست | نتیجه |
|---|---|
| درخواست بدون توکن | رد درخواست با کد ۴۰۱ |
| ورود با اطلاعات درست | دریافت موفق توکن JWT |
| درخواست با توکن معتبر | دریافت پاسخ با کد ۲۰۰ |
| ارتباط پراکسی با سرویس داخلی | موفق |

در مجموع، سه تست اصلی پروژه رو روی سیستم خودم انجام دادم و نتیجه‌ها مطابق چیزی بود که انتظار داشتم.

### نکات امنیتی پروژه

در این پروژه، توکن‌های JWT با الگوریتم HS256 امضا می‌شن و زمان انقضا دارن.

کلید محرمانه مربوط به امضای توکن داخل فایل تنظیمات محیطی قرار داره و نباید در کد اصلی یا مخزن عمومی منتشر بشه.

همچنین پراکسی بعد از بررسی توکن، درخواست رو به سرویس داخلی منتقل می‌کنه و نیازی نیست اطلاعات احراز هویت کاربر رو به سرویس قدیمی بفرسته.

البته این پروژه بیشتر برای یادگیری و انجام کارخانگی طراحی شده. اگه بخوایم در یک سیستم واقعی از اون استفاده کنیم، بهتره HTTPS، محدودیت تعداد تلاش‌های ورود و روش امن‌تری برای مدیریت حساب‌های کاربران هم اضافه کنیم.

### توقف پروژه

برای متوقف کردن سرویس‌ها از دستور زیر استفاده می‌کنیم:

</div>

```powershell
docker compose down
```
