  <h1>جواب سوال اول:</h1>
  تفاوت‌های اصلی نسخه‌های مختلف HTTP به این صورته:

**نسخه ۰.۹ پروتکل HTTP:** خیلی ساده بود، فقط متد GET داشت و هدر هم نداشت.

**نسخه ۱.۰ پروتکل HTTP:** هدرها، کدهای وضعیت و متدهایی مثل POST و HEAD اضافه شدن. معمولاً برای هر درخواست یک اتصال جدا ایجاد می‌شد.

**نسخه ۱.۱ پروتکل HTTP:** اتصال‌های پایدار یا Keep-Alive، قابلیت Pipelining و هدر Host اضافه شدن.

**نسخه ۲ پروتکل HTTP:** از قابلیت Multiplexing استفاده می‌کنه؛ یعنی چند درخواست می‌تونن هم‌زمان روی یک اتصال ارسال بشن. همچنین هدرها رو فشرده می‌کنه.

**نسخه ۳ پروتکل HTTP:** به‌جای پروتکل TCP از QUIC استفاده می‌کنه که روی UDP ساخته شده. این نسخه مشکل Head-of-Line Blocking رو هم در سطح اتصال TCP برطرف می‌کنه.

**چرا HTTP/3 از UDP استفاده میکند؟**

چون QUIC روی UDP پیاده‌سازی شده و امکاناتی مثل انتقال مطمئن داده‌ها، کنترل ازدحام و رمزنگاری رو خودش مدیریت می‌کنه. این کار باعث می‌شه ارتباط سریع‌تر برقرار بشه و اگه یک بسته گم بشه، بقیه جریان‌ها مجبور نباشن منتظر اون بمونن.




<h1>جواب سوال دوم:</h1>
الف) تفاوت این دو مدل

در ارتباط Stateful، سرور وضعیت قبلی کاربر رو نگه می‌داره و می‌تونه از اطلاعات درخواست‌های قبلی استفاده کنه. ولی در Stateless، هر درخواست مستقل از درخواست‌های قبلی بررسی می‌شه و سرور به‌صورت پیش‌فرض وضعیت کاربر رو بین درخواست‌ها نگه نمی‌داره.

ب) HTTP کدوم نوعه؟

پروتکل HTTP از نوع Stateless هست. یعنی مثلاً وقتی کاربر لاگین می‌کنه، خود HTTP به‌تنهایی نمی‌تونه تشخیص بده درخواست بعدی هم مربوط به همون کاربره.

برای حل این مشکل از روش‌هایی مثل Cookie، Session و Token استفاده می‌کنیم. مثلاً بعد از لاگین، سرور یک شناسه Session به کاربر می‌ده و مرورگر اون رو در درخواست‌های بعدی می‌فرسته تا سرور بتونه کاربر رو شناسایی کنه.

<h1>جواب سوال سوم:</h1>


<h3>الف) مشکل اصلی چیه؟
</h3>
در پروتکل HTTP معمولی، ارتباط از طرف کلاینت شروع می‌شه و سرور در جواب درخواست اطلاعات می‌فرسته. مثلاً اگه یک پیام جدید در چت دریافت بشه، سرور نمی‌تونه بدون وجود یک سازوکار مناسب، خودش یک پاسخ جدید به مرورگر بفرسته. این موضوع برای چت، اعلان‌های لحظه‌ای و سیستم‌های هشدار مشکل ایجاد می‌کنه.

<h3>ب) راهکارهای حل مشکل
</h3>
۱. روش Polling

در این روش، کلاینت هر چند ثانیه یک‌بار به سرور درخواست می‌فرسته تا ببینه اطلاعات جدیدی وجود داره یا نه. پیاده‌سازی اون ساده‌ست، ولی اگه درخواست‌ها زیاد باشن، فشار اضافی به سرور وارد می‌شه.

۲. روش Long Polling

اینجا کلاینت درخواست می‌فرسته، ولی سرور اگه اطلاعات جدیدی نداشته باشه، فوراً جواب نمی‌ده و درخواست رو برای مدتی باز نگه می‌داره. وقتی اطلاعات جدید رسید، جواب رو می‌فرسته و کلاینت دوباره درخواست جدید ایجاد می‌کنه. این روش نسبت به Polling معمولی درخواست‌های بی‌فایده کمتری داره.

۳. روش WebSocket

با استفاده از WebSocket یک ارتباط دوطرفه و پایدار بین کلاینت و سرور برقرار می‌شه. یعنی بعد از ایجاد اتصال، هر دو طرف می‌تونن بدون فرستادن درخواست جدید HTTP برای هر پیام، اطلاعات بفرستن. این روش برای چت آنلاین و بازی‌های لحظه‌ای خیلی مناسبه.

۴. روش Server-Sent Events یا SSE

در این روش، کلاینت یک اتصال HTTP باز می‌کنه و سرور می‌تونه از طریق همون اتصال، اطلاعات جدید رو به‌صورت پیوسته بفرسته. ارتباط یک‌طرفه از سرور به کلاینت هست و برای اعلان‌ها و نمایش اطلاعات زنده مناسبه.

۵. روش Webhook

در روش Webhook به‌جای اینکه یک سیستم مرتب از سیستم دیگه سؤال کنه، وقتی اتفاق مشخصی رخ بده، سیستم اول یک درخواست HTTP به آدرس از قبل تعیین‌شده سیستم دوم می‌فرسته. مثلاً درگاه پرداخت بعد از پرداخت موفق به سرور فروشگاه خبر می‌ده. البته این روش بیشتر برای ارتباط بین سرورها استفاده می‌شه.

<h1>جواب سوال چهارم:</h1>
آدرس داده‌شده:

ss://asghar:1234!!@ss.myproxy.com:1234#shadowSocks1

اجزای این آدرس به این صورته:

**طرح آدرس یا Scheme:** مقدار اون ss هست که مربوط به Shadowsocks می‌شه.

**نام کاربری یا Username:** مقدار اون asghar هست.

**رمز عبور یا Password:** مقدار اون !!1234 هست.

**آدرس سرور یا Host:** مقدار اون ss.myproxy.com هست.

**شماره پورت یا Port:** مقدار اون 1234 هست.

**بخش Fragment:** مقدار اون shadowSocks1 هست.

بخش قبل از علامت @ اطلاعات کاربر رو مشخص می‌کنه و بخش بعد از اون آدرس سرور و شماره پورت رو نشون می‌ده. همچنین قسمت بعد از علامت # یک بخش Fragment هست که اینجا می‌تونه به‌عنوان نام یا برچسب اتصال استفاده بشه.

البته این تجزیه بر اساس ساختار عمومی آدرس‌های اینترنتی انجام شده و لزوماً به این معنی نیست که این قالب برای همه کلاینت‌های Shadowsocks معتبر باشه.

<h1>جواب سوال پنجم:</h1>
۱. دیتابیس مشکل پیدا کرده و ورود به حساب انجام نمی‌شه.

**کد وضعیت: 503**

این کد به معنی در دسترس نبودن سرویس یا Service Unavailable هست. چون سرویس به دلیل مشکل دیتابیس فعلاً نمی‌تونه درخواست‌ها رو انجام بده. اگه مشکل یک خطای داخلی غیرمنتظره باشه، کد 500 به معنی Internal Server Error هم می‌تونه مناسب باشه.

**۲. نام کاربری واردشده وجود نداره و ورود ناموفق بوده.**

**کد وضعیت: 401**

این کد به معنی Unauthorized هست. چون اطلاعات احراز هویت معتبر نیست و کاربر نتونسته وارد حساب بشه. بهتره پیام خطا مشخص نکنه که نام کاربری وجود نداره یا رمز عبور اشتباهه.

**۳. وب‌سایت به دامنه جدید منتقل شده.**

**کد وضعیت: 301**

این کد به معنی Moved Permanently هست. چون آدرس سایت برای همیشه تغییر کرده و بهتره کاربر به آدرس جدید هدایت بشه. اگه انتقال موقتی باشه، می‌تونیم از کد 302 به معنی Found استفاده کنیم.

**۴. تعداد درخواست‌های کاربر از حد مجاز بیشتر شده.**

**کد وضعیت: 429**

این کد به معنی Too Many Requests هست. چون کاربر در مدت مشخصی درخواست‌های زیادی فرستاده و محدودیت تعداد درخواست‌ها رو رد کرده.

**۵. توکن JWT با موفقیت تمدید شده و داخل هدر برگشته.**

**کد وضعیت: 200**

این کد به معنی OK هست. چون درخواست با موفقیت انجام شده و سرور توکن جدید رو برگردونده. اگه پاسخ هیچ بدنه‌ای نداشته باشه، کد 204 به معنی No Content هم انتخاب مناسبیه.

**۶. کاربر از یک محدوده آی‌پی ممنوعه درخواست فرستاده.**

**کد وضعیت: 403**

این کد به معنی Forbidden هست. چون سرور درخواست رو دریافت کرده، ولی به دلیل محدودیت دسترسی اجازه استفاده از سرویس رو نمی‌ده.

<h1>جواب سوال ششم:</h1>
۱. استفاده از سرورهای داخلی دانشگاه برای دریافت پکیج‌ها

این مورد می‌تونه یک Caching Forward Proxy باشه.

چون درخواست‌های کاربران دانشگاه از طریق سرور داخلی انجام می‌شه و پکیج‌هایی که قبلاً دریافت شدن، می‌تونن از حافظه Cache همون سرور ارائه بشن. البته اگه دانشگاه یک مخزن مستقل و همگام‌شده داشته باشه، به اون Repository Mirror هم می‌گیم.

۲. تقسیم درخواست‌ها بر اساس موقعیت جغرافیایی

این مورد معمولاً با Reverse Proxy یا Load Balancer جغرافیایی انجام می‌شه.

چون درخواست کاربر بر اساس موقعیت جغرافیایی به سرور مناسب هدایت می‌شه. مثلاً کاربری که در اروپا قرار داره، به یک سرور اروپایی وصل می‌شه تا تأخیر کمتری داشته باشه.

۳. اضافه کردن احراز هویت به یک سرویس قدیمی

اینجا از Reverse Proxy همراه با Authentication استفاده می‌کنیم.

چون می‌تونیم یک Reverse Proxy جلوی سرویس قدیمی قرار بدیم تا قبل از فرستادن درخواست به اون، هویت کاربر رو بررسی کنه. این‌طوری بدون تغییر دادن کد اصلی سرویس، قابلیت احراز هویت اضافه می‌شه.
